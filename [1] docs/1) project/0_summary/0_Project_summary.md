# 미국 대기오염물질 배출시설 규제 Compliance AI 서비스

## 요약

"이 규정, 우리 공장에 적용되나요?"

미국 공장이 환경청(EPA)에 이렇게 물으면 답장까지 보통 101일이 걸립니다. 4건 중 1건은 6개월이 걸립니다.

기다리는 동안에도 서류는 내야 합니다. 틀리면 서명한 책임자가 개인 책임을 지고, 갱신이 늦으면 공장이 멈춥니다. 대상 공장 10곳 중 3곳에 이미 위반 이력이 있습니다.

답은 957쪽 규정집 안에 이미 있습니다. 찾아 주는 사람이 없을 뿐입니다.

이 서비스는 그 자리에서 근거 조문을 찾아 줍니다.

17일 · 1인 개발 · PR 266개 · 정답 조문 적중률 69% → 93% (2026.09.10 ~ 09.26)

17일 중 5일은 코드 없이 문제 정의에만 썼습니다.

실제 사용자에게 묻기 위해 텍사스 공장 환경 담당자 45명에게 직접 콜드메일을 보냈습니다.

## 프로젝트 배경

- 대기오염물질을 배출하는 미국 제조업 공장은 공장을 운영하기 위해 규제 준수 인증 문서를 주기적으로 작성해야 합니다.
  - [근거] 40 CFR 70.6(a)(3)(iii), 70.6(c)(5), 70.5(a)(1)(iii)

- 문서를 작성할 때, 공장 상황에 규정의 어떤 조항이 적용되는지 밝혀야 합니다.
  - [근거] 텍사스 TCEQ, Title V Deviation Reporting and Permit Compliance Certification Guidance

### 문제 인식과 해결

Q. 규정 찾는 게 정말 어렵나?

A. PDF로 957쪽이고, 규정이 자주 바뀝니다. (2018~2025년 136건, 현재 조문의 45%)

S. 질문창에 공장 상황을 입력하면, RAG(질문과 관련된 규정만 골라 AI에게 건네주는 방식)가 후보 규정을 10개로 좁혀 줍니다.

Q. AI에 물어보면 안 되나?

A1. 규정이 너무 커서 컨텍스트(AI가 한 번에 읽을 수 있는 양)에 다 들어가지 않습니다. (957쪽, 463만 토큰. 토큰은 AI가 글을 세는 단위)

A2. 학습 시점 이후의 최신 개정 내용을 반영하지 못합니다.

S. RAG로 해결했습니다.

Q. 한 번 작성하고 매번 똑같이 작성하면 안 되나?

A. 규정이 계속 바뀝니다. (2018~2025년 136건, 현재 조문의 45%)

S. 데이터셋을 자동으로 최신화하는 기능을 만들었습니다. LLM이 하지 못하는 일입니다.

### 서비스 타겟 설정

Q. 타겟은 누구인가?

A. 위반 이력이 있는 미국 공장의 환경 담당자입니다.

Q. 왜 타겟을 그렇게 잡았나?

A. 위반 이력이 있는 공장은 약 13,800곳(대상 49,618곳 중 27.9%)입니다. 이미 위반을 겪어서, 규정을 제대로 확인해야 할 이유가 가장 분명한 곳이라고 생각했습니다.

Q. 왜 한국이 아닌 미국 공장을 대상으로 서비스 타겟을 잡았나?

A. 규정 적용 여부를 물으면, 한국은 14일 안에 답할 의무가 있지만 미국 환경청은 의무가 없고 회신 중앙값이 101일입니다. 답을 기다리는 시간이 더 긴 미국에 수요가 더 있을 것이라고 생각했습니다.

### 서비스

Q. 이 서비스는 어떤 서비스인가?

A. 대기오염물질 배출 허가를 받은 미국 제조업 공장의 담당자가 규제 준수 인증 문서를 작성할 때, 공장에 적용될 수 있는 조항 후보와 무엇을 확인해야 하는지를 최신 근거 조문과 함께 정리해 주는 서비스입니다.

Q. 꼭 조항에 근거해서 문서를 작성해야 하나?

A. 공식 매뉴얼에서 정하고 있습니다.
[근거] 텍사스 TCEQ, Title V Deviation Reporting and Permit Compliance Certification Guidance

S. 서비스 답변의 근거를 규정 원문으로 구조적으로 강제했습니다.

Q. 가장 핵심 기능은 무엇인가?

A. 공장의 상황을 입력하면, 적용될 만한 규정 후보를 근거 원문과 함께 제공합니다.

### 데이터

Q. 사용한 데이터셋은?

A. 규정 원문(eCFR), 변경 알림 데이터(Federal Register), 위반 이력 데이터(EPA, ECHO), 공개된 질의 답변 모음 데이터(EPA, ADI/CAA)입니다.

Q. 데이터 신뢰성 확보를 위한 노력은?

A. 수집·파싱(원문을 조항 단위로 쪼개기)·적재(데이터베이스에 넣기) 단계마다 예측과 실제를 맞춰 봐서, 어긋난 곳 17개를 찾아 고쳤습니다.

Q. 데이터 일관성 확보를 위한 노력은?

A. 테이블(데이터를 담는 표) 43개마다 규칙을 세우고, 규칙에 어긋나면 코드 병합이나 데이터 공개를 자동으로 막았습니다. 예를 들어 자동 갱신 때 "규정 글이 사라졌다"는 경고로 공개가 멈췄습니다. 확인해 보니 수식 기호(|)를 한쪽에서만 지운 탓이었고, 검사를 고친 뒤 다시 공개했습니다.

Q. 데이터 추적성 확보를 위한 노력은?

A. 모든 적재에 버전을 붙이고, 원본은 손대지 않고 보관했습니다. 개정 공지(FR) 수집이 요청 제한에 걸려 1,533건 중 384건만 받은 버전이 공개됐을 때, 직전 버전(1,532건)으로 바로 되돌렸습니다.

Q. 데이터 최신성 확보를 위한 노력은?

A. 원본마다 바뀌는 주기를 확인하고, 그 주기에 맞춰 적재 일정을 세웠습니다. 규정 원문(eCFR)과 개정 공지(FR)는 매일, 위반 이력(ECHO)은 EPA가 일요일에 갱신하므로 매주 화요일에 받습니다. 질의 답변 모음(ADI)은 수동으로 받습니다.

### 답변 신뢰성

Q. 이 서비스가 주는 답변을 어떻게 믿을 수 있나?

A. RAG 검색·답변 품질을 개선했습니다.

S. 다양한 실험을 통해 정답 조문 적중률(Hit@5: 정답 조문이 검색 결과 상위 5개 안에 드는 비율)을 69% → 93%로 개선했습니다. (실제 EPA 판정서한 102건 기준. 판정서한은 EPA가 공장 질문에 공식으로 답한 편지)

**검색 개선**

| 실험 이유 | 실험 내용 | 실험 결과 | 판단 |
|---|---|---|---|
| 법률 특화 임베더(글을 숫자로 바꿔 비슷한 글을 찾게 하는 모델)가 효과 있나? | bge-m3(일반) vs Kanon 2(법률 특화) | 적중률 49% → 69% | 채택. 가장 큰 차이 |
| 정답을 찾지만 순서가 뒤로 밀림 | Kanon 2 리랭커(찾은 후보의 순서를 다시 매기는 모델) 추가 | 69% → 80% | 채택. 다른 리랭커 2개보다 높음 |
| 키워드 검색이 꼭 필요한가? | 하이브리드(BM25: 같은 단어가 겹치는 글을 찾는 검색) 추가 | 80% → 80% (Recall@20: 정답이 상위 20개 안에 드는 비율 +0.03) | 채택. 후보 폭이 넓어짐 |
| 의미 없는 부록 표가 앞에 섞임 | 부록 표는 뒤로, 찾은 Subpart(같은 주제의 조항 묶음) 우선 | 80% → 88% | 채택 |
| 아직 정답이 앞에 덜 옴 | LLM 리랭크(gpt-5-mini가 순서를 한 번 더 매김) 추가 | 88% → 93% | 채택. 질문당 약 20초·$0.006 늘지만 서류 작성용이라 감수 |

Q. 7%는 놓치는데, 틀리면 누가 책임지나?

A. 이 서비스는 "적용된다"고 판정하지 않습니다. 조항 후보와 근거 원문을 주고, 최종 판단과 서명은 담당자가 원문을 직접 확인한 뒤 합니다.

S. 답 형식에서 판정 칸을 없애 "적용됩니다"를 구조적으로 쓰지 못하게 했고, 모든 말에 근거 조문을 붙였습니다.

### 서비스 유효성 검증 (콜드메일)

Q. 이 서비스가 정말 필요한 서비스인지 검증했나?

A. 검증하기 위해 텍사스 공장 45곳의 환경 담당자 45명에게 콜드메일을 보냈습니다.

Q. 어떤 방식으로 메일 주소를 얻고 검증했나?

A. 위반 이력 공장을 추출하고, 검색으로 이메일 주소를 알아낸 뒤, Hunter.io(이메일 주소가 진짜인지 확인해 주는 서비스)로 검증했습니다.

Q. 왜 텍사스 공장에만 보냈나?

A. 텍사스주가 위반 내역과 과징금 규모가 가장 커서 표본으로 적합하다고 생각했습니다. (EPA, ECHO)

Q. 45건은 너무 작은 것 아닌가?

A. Hunter.io 무료 크레딧 제한 때문입니다. 텍사스의 회신 결과를 보고, 메일 추출 과정을 검토한 뒤 늘릴 계획입니다.

Q. 무엇을 물어봤나?

A. 현재 어떻게 문제를 해결하고 있는지, 한 달에 몇 시간이 드는지, 어떤 서비스가 있으면 편할지 등을 물었습니다.

Q. 물어보는 것은 문제 정의 전에 하는 것이 맞지 않나?

A. 이 조사를 먼저 하고 문제를 정의했다면 더 좋은 서비스가 됐을 것이라고 뒤늦게 깨달았습니다. 지금은 제 문제 정의가 현실을 잘 반영하는지 검증하는 용도로 쓰고 있지만, 다음 프로젝트부터는 이 과정을 먼저 하겠습니다.

Q. 답변은 받았나?

A. 아직 없습니다. 메일 추출 과정을 검토한 뒤 더 많은 곳에 보낼 계획입니다.

### 프로젝트

Q. 얼마나 진행했나?

A. 9/10(목)~9/26(토), 총 17일입니다.

Q. 팀으로 진행했나?

A. 혼자 진행했습니다.

Q. 왜 혼자 했나?

A. 서비스를 처음부터 끝까지 책임지는 경험을 해 보고 싶었습니다. 또 에이전트를 지휘하며 1인 생산성을 극대화해 보고 싶었습니다.

Q. 얼마나 몰두했나?

A. 하루 11~12시간 몰두했습니다. 토큰 사용량 16.7억(캐싱 16.3억 + 입출력 0.4억), PR 266개, 테스트 772개, 티켓 288개입니다.

### 주요 결정

Q. 직접 내린 주요 결정은?

A1. 답에서 판정 칸을 없앴습니다. "참고용"이라는 문구로는 사람의 행동이 바뀌지 않는다고 봤습니다.

A2. LLM 리랭크를 넣었습니다. 질문당 약 20초가 늘지만, 채팅이 아니라 서류 작성용이라 감수했습니다.

A3. 점수가 올라도 "Subpart A(모든 공장에 공통인 조항) 조문 3개 항상 넣기"는 버렸습니다. 검색이 찾아서가 아니라 억지로 끼워 넣어서 오른 점수였고, 비용도 약 27% 늘었습니다.

A4. 테스트와 구현을 다른 AI에게 맡겼습니다. 한 AI가 둘 다 하면 자기 코드에 맞춰 테스트를 고칠 수 있습니다.

### 개발 방식

Q. 어떤 방식으로 개발했나?

A. 테스트 기반 개발을 자동화하고, 에이전트를 지휘해 개발했습니다.

Q. 왜 테스트 기반 개발을 했나?

A. AI가 짠 코드를 검증하기 위해서입니다. 그래서 "완성"의 기준을 테스트로 정하고, 테스트가 통과해야 병합하게 했습니다.

Q. 어떤 것을 테스트했나?

A. 데이터를 제대로 모으는지, 맞는 조항을 찾는지, 근거를 붙여 답하는지, 화면이 잘 돌아가는지 확인했습니다. 예를 들어 표의 줄과 칸이 유지되는지 보는 테스트가, 규정 표가 한 줄로 뭉개져 기준 숫자가 어느 줄 것인지 알 수 없게 된 버그를 잡았습니다.

Q. 에이전트는 어떻게 사용했나?

A. 테스트를 쓰는 에이전트(Claude Code)와 코드를 짜는 에이전트(Codex)를 나눴고, 병합은 사람이 직접 했습니다. (둘 다 AI 코딩 도구)

| 누가 | 한다 | 안 한다 |
|---|---|---|
| 사람 | 아이디어, 티켓 확인, PR 확인과 병합 | 코드 작성 |
| Claude Code | 티켓, 설계, 실패하는 테스트 작성 | 기능 구현 |
| Codex | 기능 구현, PR 생성 | 테스트 수정·삭제, PR 병합 |
| Linear (할 일 관리 도구) | 티켓 보관, 진행 상태 관리 | 코드·테스트 보관 |
| GitHub (코드 저장소) | 코드 보관, CI 자동 검사, 배포 시작 | 사람 승인 없는 병합 |
| Slack (메신저) | PR·CI·병합·배포 결과 알림 | 판단·실행 |

사람 (아이디어·승인)
→ Claude Code (설계 + 테스트 작성)
→ Linear (티켓 발행)
→ Codex (구현 + PR)
→ CI (규칙에 맞게 잘 되었는지 자동 검사)
→ 사람 (승인)
→ CD (Render·Vercel 자동 배포)
→ Slack (알림)

Q. 사용한 기술 스택은?

- Language: Python
- DB: PostgreSQL(Supabase)
- Backend: FastAPI, Render
- Frontend: Next.js, React, Tailwind CSS, Vercel
- CI/CD: GitHub Actions
- TDD 개발 자동화 Flow
    - 설계: Claude Code
    - 티켓 관리: Linear
    - 구현, 테스트: Codex
    - CI/CD: GitHub Actions, Render, Vercel
    - 알림: Slack
    - 코드 버전 관리: GitHub
