# Compliance AI · TDD 개발 자동화

## TDD 개발 자동화

> Claude가 실패하는 테스트를 쓰고, Codex는 통과만 시킵니다.

### 흐름

```text
[사람]    구현하고 싶은 기능을 Claude Code(Plan Mode)에 초안 생성 요청
  |
[Claude] 초안 제시
  |
[사람]    수정 사항 Claude Code에 지시
  |
[Claude] 수정안 제시
  |
[사람]    승인 후 Linear 티켓 발행 지시
  |
[Claude] Linear 티켓 발행해서 변경 범위·완료 기준·설계 파일 작성 + 실패하는 테스트 시나리오 작성
  |
[Codex]  테스트를 통과하는 코드 구현 → GitHub PR 생성
  |
[CI]     GitHub Action, <테스트 + 이름 규칙 + 설계 파일 + 데이터 계약 + 품질 합격선> CI 검사
  |
[사람]   PR 확인 → 직접 merge
  |
[CD]    merge되면 Render(백엔드) · Vercel(프론트) 자동 배포
  |
[알림]  Slack에 모든 과정 알림
```

### 1인 개발이 가능했던 이유

1. "완성"이 코드보다 먼저 있습니다.
    - Claude가 실패하는 테스트를 먼저 씁니다. AI의 말이 아니라 테스트의 초록불이 완료입니다.
2. 테스트 설계 에이전트와 실행 에이전트를 분리했습니다.
    - Codex는 테스트를 고치거나 지울 수 없습니다(작업 규칙으로 금지). 자기 코드에 맞춰 테스트 시나리오를 고치는 일을 구조로 막았습니다.
3. 옛 기능이 깨지면 병합 전에 압니다.
    - PR 254개 × 테스트 772개. 손으로 254번 확인했다면 불가능한 일입니다.
4. 사람은 코드가 아니라 약속을 검토합니다.
    - "이 테스트가 무엇을 보장하는가"만 보고 병합합니다. 그래서 혼자서 17일에 PR 254개가 가능했습니다.

병합만은 자동화하지 않았습니다. 마지막 판단은 사람이 합니다.

### 역할

| 누가 | 한다 | 안 한다 |
|---|---|---|
| 사람 | 아이디어, 티켓 확인, PR 확인과 병합 | 코드 작성 |
| Claude Code | 티켓, 설계, 실패하는 테스트 시나리오 작성 | 기능 구현 |
| Codex | 기능 구현, GitHub PR 생성 | 테스트 수정·삭제, GitHub PR 병합 |
| Linear | 티켓 보관, 상태판 (Todo → In Progress → In Review → Done) | 코드·테스트 보관 |
| GitHub | 코드 보관, PR, CI 검사(테스트 + 규칙 + 합격선), CD 배포 트리거 | 사람 승인 없는 병합, main 직접 push |
| Slack | PR 열림·CI 실패·병합·배포 결과 알림 | 판단·실행 (알림만 받음) |

**Q.** 왜 테스트 작성자와 구현자를 나눴나? 한 에이전트가 다 하면 빠르지 않나?

**A.** 빠르지만, 한 에이전트가 둘 다 쓰면 자기 코드에 맞춰 테스트를 고칠 수 있음. 또 서로의 컨텍스트가 오염이 안됨.

**Q.** 나누면 해결되나?

**A.** 테스트는 Claude가 설계 단계에서 먼저 쓰고, Codex는 테스트를 건드리는 것이 규칙으로 금지했습니다. "무엇이 완성인가"를 정하는 쪽과 "만드는" 쪽이 달라야 검증이 의미가 있다고 생각합니다.

**Q.** 병합은 왜 사람이 하나?

**A.** AI에 모든 것을 위임하지 않습니다. 중요한 판단은 사람이 개입하도록 하였습니다.
